# ГрузоПоиск

Информационная система-агрегатор заказов на грузоперевозки для частных водителей и малых транспортных компаний.

Репозиторий лабораторных работ по дисциплине «Методы и средства проектирования информационных систем».

## Описание

ГрузоПоиск собирает заказы на перевозку в одну ленту. Грузоотправитель или брокер публикует груз через форму на сайте, а водитель открывает ленту, выбирает подходящий заказ по маршруту, массе, кузову и цене и смотрит его карточку с контактами. Заказы с других площадок (Avito, АТИ, Telegram) хранятся с пометкой источника. Система работает в двух контейнерах: приложение FastAPI (страницы на Jinja2 и Bootstrap 5.3.8) и база PostgreSQL 18.

## Функции

| Функция | Кто | Адрес |
|---|---|---|
| Публикация заказа на перевозку: маршрут, груз, масса, объём, кузов, дата загрузки, стоимость, оплата, контакты и срочность | Грузоотправитель, брокер | `/orders/new` |
| Просмотр ленты заказов (новые сверху) и карточки заказа | Все роли | `/orders`, `/orders/{id}` |
| Отказ: кто пытался, что хотел сделать и почему система не дала | Все роли | `/access-denied` |
| Уведомление водителю о новом заказе, счётчик непрочитанных, кнопка «Прочитано» | Водитель | `/notifications` |
| Срочность заказа (новое в 0.0.6): «Обычный» или «Срочный», видна в форме, в списке и в карточке | Грузоотправитель, брокер задают, все видят | `/orders/new`, `/orders` |
| Резервная копия базы и восстановление из неё (новое в 0.0.6) | Администратор | `docker compose run --rm backup` и `restore` |

## Правила

- Роль выбирается переключателем в шапке, по умолчанию «Водитель». Входа по паролю пока нет.
- Публиковать заказы могут только грузоотправитель и брокер. Водитель, администратор и владелец системы попадают на страницу отказа.
- Обязательно заполнить название груза, города откуда и куда, массу, стоимость, дату загрузки и контакты. Масса до 40 т, объём до 200 м³, стоимость целым числом в рублях, дата загрузки не в прошлом и не дальше года, города отправления и прибытия не совпадают. Тип кузова, оплата и срочность выбираются только из списка.
- Если срочность не выбрана, заказ получает «Обычный». Заказы, созданные до версии 0.0.6, тоже показываются как «Обычный».
- О каждом опубликованном заказе водитель узнаёт из уведомления, связанного с этим заказом.
- Структуру базы меняют только миграции Alembic (`app/migrations/versions`), они применяются сами при запуске приложения. Отдельных команд миграции выполнять не нужно.
- Перед обновлением на новую версию снимается резервная копия базы. Старые теги образа не перезаписываются, на них держится откат.

## Резервная копия

В `docker-compose.yml` есть два служебных сервиса на образе `postgres:18`. При обычном `docker compose up -d` они не запускаются, у них стоит `profiles: ["tools"]`.

```text
docker compose run --rm backup
docker compose run --rm restore
```

`backup` выполняет `pg_dump` и кладёт файл `backup/app.sql` рядом с `docker-compose.yml`. Это логическая, горячая, полная копия: база работает, пока копия снимается. Папка `backup` в `.gitignore`, копии с данными в репозиторий не попадают.

`restore` выполняет `psql -f /backup/app.sql`. Восстанавливать нужно на поднятую базу без приложения: `docker compose up -d db`, затем `restore`, затем `docker compose up -d`. В копию попадает и таблица `alembic_version`, поэтому после восстановления приложение миграции заново не применяет.

Откат на версию 0.0.5: `docker compose down -v`, `docker compose up -d db`, `docker compose run --rm restore` с копией, снятой до обновления, затем `git checkout lab5` и `docker compose up -d`.

## Лабораторная работа 6. Выпуск версии 0.0.6

Новое поле у заказа: «Срочность» (`urgency`, «Обычный» или «Срочный»). Водителю важно сразу видеть, какой груз надо забрать срочно. Поля нет в ER-диаграмме третьего курса, оно добавлено к сущности Order этой работой.

Миграции: Alembic 1.20.1 (с SQLAlchemy 2.1.9), папка `app/migrations`. Миграция `0001` описывает структуру пятой работы через `CREATE TABLE IF NOT EXISTS`, поэтому на базе пятой работы ничего не меняет, а Alembic только записывает в `alembic_version`, что шаг применён. Миграция `0002` добавляет столбец `urgency VARCHAR(20) NOT NULL DEFAULT 'Обычный'`, старые заказы сразу получают «Обычный». Миграции применяет `app/migrate.py` при старте приложения, код создания таблиц при старте убран.

Образ приложения: `sideseer/mispisit-lab1:0.0.6` (linux/amd64 и linux/arm64). В `docker-compose.yml` у сервиса `app` только `image`, строки `build` нет. Имя проекта `mispisit-akhmetzhanov` то же, поэтому 0.0.6 встаёт на тот же том `dbdata`.

Сборка и публикация образа:

## Лабораторная работа 5. Уведомление о новом заказе

Выбран вариант «уведомление». Событие: успешная публикация заказа грузоотправителем или брокером. Водителю об этом нужно узнать, поэтому приложение записывает строку в новую таблицу `notifications` и показывает её на странице `/notifications`. Сообщение связано с конкретным заказом (номер, маршрут, масса), а не с заготовленной фразой. До публикации список пустой, в шапке есть пункт «Уведомления» и счётчик непрочитанных.

Таблица создаётся при старте приложения так же, как таблицы третьей работы (`CREATE TABLE IF NOT EXISTS`), инструмент миграций не подключался. Поэтому обновление с версии 0.0.4 не стирает уже сохранённые заказы: том `dbdata` остаётся, новая таблица появляется рядом.

Экран оформлен тем же Bootstrap 5.3.8. Три функции и страница отказа работают как раньше. Вариант «наблюдение за системой», отдельный `worker`, Mailpit и Prometheus в эту работу не входят.

Образ приложения: `sideseer/mispisit-lab1:0.0.5` (linux/amd64 и linux/arm64). В `docker-compose.yml` у сервиса `app` только `image` с тегом `0.0.5`, строки `build` нет. Имя проекта `mispisit-akhmetzhanov`, том `dbdata` и база `postgres:18` те же.

## Лабораторная работа 3. Постоянное хранение данных

Заказы теперь хранятся в PostgreSQL 18 (официальный образ `postgres:18`), который работает вторым
сервисом рядом с приложением. Файл `docker-compose.yml` описывает два сервиса:

- `app` это готовый опубликованный образ `sideseer/mispisit-lab1:0.0.3` (linux/amd64 и linux/arm64), строки `build` нет;
- `db` это база PostgreSQL 18, её файлы лежат в именованном томе `dbdata` (путь `/var/lib/postgresql`,
  так требует образ PostgreSQL 18), порт базы наружу не открыт.

Имя проекта `mispisit-akhmetzhanov` задано строкой `name`, поэтому том называется
`mispisit-akhmetzhanov_dbdata` и не пересекается с чужими проектами. У базы есть `healthcheck`
(`pg_isready`), приложение стартует только после него (`condition: service_healthy`).
Логин, пароль и имя базы учебные (`app`), их задаёт `docker-compose.yml` через переменные окружения,
приложение подключается по имени сервиса `db` (`DATABASE_URL`).

При первом запуске приложение само создаёт таблицы `data_sources` (источники заказов: Сайт ГрузоПоиск,
Avito, АТИ, Telegram) и `orders` (заказы). Демо-заказов нет, список заказов после запуска пустой.
Названия таблиц и полей взяты из ER-диаграммы ЛР5 3 курса (сущности DataSource и Order).
Публиковать заказы могут Грузоотправитель и Брокер, Водитель только смотрит.

Проверка сохранности: создать заказ, выполнить `docker compose down`, потом `docker compose up -d`,
заказ остаётся в списке.

Сборка и публикация образа:

```bash
docker buildx build --platform linux/amd64,linux/arm64 -t sideseer/mispisit-lab1:0.0.3 --push .
```

## Лабораторная работа 2. Три главные функции и страницы

Платформа прежняя: FastAPI (Python 3.14), страницы собирает шаблонизатор Jinja2. Один контейнер, порт 8080. После запуска приложение открывается по адресу http://localhost:8080

| Функция | Кто это делает | Что происходит | Адрес |
|---|---|---|---|
| Создать заказ на перевозку | Грузоотправитель (в лабе 2 роль называлась «Заказчик») | Изменение данных | /orders/new |
| Посмотреть заказы (список и карточка) | Водитель | Просмотр | /orders, /orders/1 |
| Попытка водителя создать заказ, ошибочные данные в форме | Водитель, Заказчик | Отказ | /access-denied |

Роль выбирается переключателем в шапке (по умолчанию «Водитель»). Создавать заказы может только заказчик.

Страницы:

- `/` главная, название продукта и переходы к действиям;
- `/orders` список заказов;
- `/orders/new` форма нового заказа;
- `/orders/1` карточка одного заказа;
- `/access-denied` отказ: кто пытался, что хотел сделать и почему система не дала.

Данные сейчас лежат в файле `app/data/orders.json` внутри контейнера: форма дописывает его, список и карточка читают. После удаления контейнера новые заказы пропадают, остаются три демо-заказа.
